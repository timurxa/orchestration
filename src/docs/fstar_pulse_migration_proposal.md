# F*/Pulse Reimplementation Proposal

**Status:** Active research. The implementation language direction and project priorities are recorded; the target API, runtime boundary, and migration plan are not yet decided.

## Current direction

Reimplement the orchestration API in `src/api` in F*/Pulse, with Pulse code extracted to OCaml as the initial execution target. KaRaMeL is not a target requirement and should not shape the design unless a specific research result makes it relevant. F*/Pulse with OCaml extraction is the current language hypothesis; the workflow formalism and API abstraction remain open to evidence. Workflow source should describe a structure that a separate runtime follows; declaring a model step must not itself call the model. The authoring interface should support ordinary user code alongside workflow constructs.

The reimplementation should include the orchestration-side Codex interface/client needed to communicate with the Codex app-server protocol. It must not reimplement the Codex Rust app-server itself. Keep the workflow API and its usage model agnostic of Codex-specific details so the orchestration system can evolve or use other backends.

This is an experiment in agentic proof-oriented programming. The most important goal is to design a correct system. Take as much care as possible to make proof obligations useful, meaningful, and connected to the system's actual guarantees. Implementation difficulty should not be a major reason to weaken the desired correctness or assurance goals.

The runtime architecture and result structure will likely differ from the current implementation because resumability will carry greater weight. Even with those changes, retain the project's central intentions: do not block the scheduler while model calls are pending, and provide structured, straightforward ways to work with LLMs.

This proposal tracks the direction, project priorities, research evidence, and unresolved decisions; it does not authorize implementation work.

## Research directions

The current orchestration implementation is in [`src/api`](../api). The directions below investigate its current semantics and possible improvements to the orchestration system. Research can range broadly across programming-language theory, workflow systems, and proof-oriented programming. The goal is to identify useful formalisms for generalizing this API, not merely to port its current syntax. Open problems below must stay narrow and request concrete, checkable results.

### Pulse and F* programming model

- What limitations does Pulse impose on user programs, types, effects, recursion, higher-order functions, and mutable state when extracted to OCaml?
- Which Pulse properties and constructs are checked by F*, and which parts of the execution model or runtime remain trusted?
- How should arbitrary user code blocks interact with workflow constructors? Which blocks should be pure total F* functions, Pulse computations, or explicit runtime operations?
- Can F* effects and Pulse preconditions/postconditions express useful restrictions on workflow callbacks, and how would those restrictions compose across a whole plan?
- What source syntax is practical using ordinary F*/Pulse functions and combinators? Which conveniences would require Meta-F*, compiler extensions, or a separate generator?

### Static workflow representation and scheduler API

- Can the current orchestration API in `src/api` be represented as a static program without Meta-F*, while still expressing its workflow structures, scheduler state, and resumable runs?
- What representations should the workflow plan, artifact state, asynchronous operations, joins, budgets, and checkpoints use?
- Which parts can be ordinary typed F* values, and which need an explicit serialized or generated representation?
- Can F* types and proofs express the current API's important invariants without compromising the project's correctness goals?
- How should static workflow structure, dynamic route decisions, runtime invocation state, and durable run state be separated?
- What stable identity and versioning scheme would let an updated executable decide whether it can resume an older run?
- How should workflow identity normalization avoid collisions, and which direct or transitive source, callback, schema, build, runtime, and environment inputs belong in the identity?
- Should checkpoint row format versions be validated independently of payload versions, and which older versions need explicit migrations?
- What must a persisted dynamic-expansion signature include so that changed raw values or omitted historical signature rows cannot silently pass resume validation?
- Must routing callbacks be rerun after restart, or may a durable workflow persist their decisions/results and keep ordinary higher-order functions transient?
- What complete version/identity tuple must a checkpoint match before the interpreter rebuilds or replays workflow code, and which mismatches require migration?

### Workflow formalisms and API generalization

Look for established formalisms that can explain, simplify, or generalize the actual constructs in `src/api`. Candidates to investigate include free and indexed-free DSLs, algebraic effects and handlers, applicative/selective/arrow interfaces, typed DAG or dataflow IRs, and event-sourced state machines or durable workflow semantics. This list is a starting point, not a limit.

For each candidate, map the current API's typed composition, `fan`/projection, `lift`, `so`, model calls, dynamic expansion, budgets, artifact dependencies, asynchronous suspension, and resume behavior into that formalism. Evaluate ordinary arbitrary user code alongside declarative workflow structure, static versus dynamic graph formation, serialization, proof obligations, and whether model calls remain nonblocking. Identify combinations where one formalism handles authoring and another handles interpretation or durable execution.

The key question is whether a formalism yields a more expressive or simpler API while making its runtime and proof obligations clearer. Do not assume F*/Pulse syntax or any one formalism is the answer in advance.

### Typed artifacts and generated code

- Can F*'s type system make the API more expressive by attaching restrictions to artifacts produced by an LLM and checking those restrictions before user code consumes them?
- What type-level or refinement-level contracts could describe generated source artifacts—for example, a C file that must satisfy specified interface, compile, or validation conditions before a later `so` block may use it?
- Could an LLM-generated C file be compiled into an executable and then run from a `so` block? What typed stages, validation obligations, and failure states would that workflow need to expose?
- How should generated programs be built, identified, and associated with their source artifact so that resume and audit can distinguish exact inputs and toolchain versions?
- What durable effect contract should represent build and process execution, including persisted intent, success, failure, timeout, truncation, and unknown outcome states?
- Should process execution be an explicit workflow operation rather than ordinary `so` callback code, and how can its outputs be safely composed with typed artifacts?
- Which termination and output-capture fields (exit status, signal, timeout, truncation, stdout/stderr identity) must be persisted to distinguish process outcomes across resume?
- Which artifact types need canonical codecs, model-output schemas, Blob/BlobTree handling, and version compatibility? Can those codecs and schemas be derived or generated reliably?

### Runtime, recovery, and external components

- Which parts of scheduling, persistence, serialization, filesystem staging, and process management should be Pulse, ordinary F*, OCaml, or a narrow foreign-function boundary?
- What state must be persisted, and which deterministic computations may be recomputed from saved artifacts without changing observable workflow results?
- Which artifact identity and dependency evidence justify reusing a known durable result without rerunning its producer, and what proof permits recomputation or replay even when some pure computation is repeated?
- How should the runtime handle an interrupted external operation whose submission or result status is unknown? Which operations can be retried safely, and what guarantees can the external service actually provide?
- What should happen when a model returns malformed output, an LLM-generated program does not compile, a process fails or stalls, storage becomes unavailable, or a run is interrupted during a checkpoint transition?
- What guarantees should hold for parallel branches, ordering, cancellation, joins, and resume after only some branch results have been persisted?
- What evidence should the runtime retain for artifacts, model attempts, conversations, work occurrences, and causal edges, and which of those are required to reconstruct or audit a run?
- What parts of the current runtime are allowed to change to support stronger resumability, and what behavioral intentions—especially nonblocking model calls and structured LLM workflows—must remain central?

### Codex app-server interface and backend independence

- What should the new F*/Pulse orchestration-side client/protocol implementation expose when communicating with the existing Codex Rust app-server?
- How can this interface remain decoupled from Codex-specific concepts while still implementing the app-server protocol correctly?
- Which inputs, permissions, workspace boundaries, tools, and result formats can the client validate and constrain before handing work to the app-server?
- Which safety properties can be proved about the wrapper, and which must remain explicit assumptions about the CLI, operating system, model service, and authentication state?
- What protocol, process-lifecycle, timeout, retry, and shutdown behavior must the interface specify so that CLI failures cannot silently corrupt workflow state?
- How should the interface represent and recover from a CLI response that arrives before its result is durably committed?
- What uniqueness, retention, and durable-acceptance guarantees apply to `clientUserMessageId` in app-server history, and how should a no-match affect an unknown attempt?
- Which client/server identity should be recorded with an external attempt: resolved executable path/version, observed `userAgent`, client protocol/schema revision, or negotiated capabilities?
- How should cancellation distinguish a request being sent from a terminal interrupted turn, given that the interrupt RPC response is separate from turn completion?

### Generality, expressiveness, and swappable abstractions

- Which parts of the current API are unnecessarily tied to one LLM provider, app-server protocol, structured-output mechanism, tool-call convention, artifact representation, or transport?
- How could the system support structured interaction through tool calls today and potentially JEV or other mechanisms later, without forcing workflow authors to depend on one protocol?
- What does “JEV-like” interaction mean for this API: a typed state-to-decision call or a stateful exchange, and should its durable context be reusable typed artifact data, protocol/session history, or both?
- Could artifacts represent context histories or other richer state, and what type, storage, and resume contracts would that require?
- Which current abstractions should be generalized to make model providers, protocols, tools, transports, and artifact forms swappable?
- How can such generalization improve flexibility and expressiveness without making common workflows harder to author or greatly increasing conceptual and implementation complexity?
- What is the smallest stable abstraction boundary that keeps workflows easy to write while permitting those future choices?
- Which guarantees around typed outputs, pending-call completion, artifact identity, and correlation must be common across backends, and which can remain adapter-specific?
- For an external attempt with an unknown outcome, what evidence or backend capability should allow retry instead of reconciliation or explicit unresolved recovery?
- Does absence from retained backend history prove definite non-acceptance, or must the attempt remain unknown until a durable policy authorizes at-least-once retry?

### Verification and trust boundaries

- What does “completely safe” mean for this system, and which safety properties are in scope: type safety, memory safety, filesystem containment, protocol correctness, schedule correctness, crash consistency, or other properties?
- How can F* proof-oriented programming establish useful end-to-end guarantees when the model provider, Codex Rust app-server, compiler, operating system, SQLite, and generated executable may fail or behave outside the verified code?
- Which external components need verified implementations, which can be covered by checked interfaces and runtime validation, and which remain trusted assumptions?
- How should assumptions about F* extraction, OCaml libraries, foreign bindings, C compilers, and generated-code toolchains be documented and checked?
- What small prototypes and proof or runtime checks would resolve the highest-risk questions before committing to a full rewrite?

### Findings by research direction

A deeper kernel inventory finds that the current “inert declaration” property is narrower than it first appears: declaration does not dispatch a model call, but raw expressions are evaluated when generated flows are rebuilt, and public `solve`/`resume` wait synchronously for the whole workflow. `so` callbacks and custom transport procedures run inline; the coordinator heartbeat advances after handling events, so a callback blocked beyond the 30-second execution lease creates a plausible competing-resume/replay hazard. The report also identifies a possible admission/checkpoint mismatch: a call admitted against global budget may drive one pool remainder negative, while checkpoint validation rejects negative remainder; the specific path is source-inferred, not reproduced at runtime. It reports a terminal unknown Codex turn status being normalized to completion despite app-server completion semantics. These are provisional findings; details, source citations, and omitted coverage are in the [API semantics inventory report](/Users/alex/areas/temp/fstar-pulse-research/api_semantics_inventory.md).

A detailed proof/failure ledger sharpened the budget issue into a source-level counterexample. With total budget 10, two equal pools, and a single 9.66 charge in one pool, admission succeeds because global remaining stays 0.34. The budget specification treats pool capacities as soft and permits a negative selected-pool remainder after recalculation, but checkpoint validation rejects negative remainder and spend above recalculated capacity. This is not a reproduced workflow crash; it is a contradiction between admission/spec and snapshot validation. Since runtime accounting uses float64, the rewrite also needs an exact or bounded arithmetic invariant. The same ledger identifies terminal Codex status `unknown` mapping to success as a source hazard. See [proof/failure ledger](/Users/alex/areas/temp/fstar-pulse-research/proof_fault_model_ledger.md).

The source-inspection pass reports that the current API already has a typed declaration/lowering boundary. `src/api/vecherinka_comptime.nim` builds and lowers typed flow declarations; runtime interpretation is in [`vecherinka_runtime.nim`](../api/vecherinka_runtime.nim). Model declarations create plan nodes and submitters; dispatch happens later, so the declaration itself does not call the model. `FlowSpec[A,B]` composition checks adjacent endpoint types at compile time. Composition, `fan`, projections, `lift`, and `so` lower to explicit runtime nodes/callbacks. The report cites `make_vecherinka`, `lower_vecherinka_runtime`, `lower_flow_expr`, `lower_fanout`, `lower_it`, `lower_lift`, `lower_so`, `lower_model_call`, `handle_invocation`, `suspend_model`, and `dispatch_model_requests`.

The static-authoring pass clarifies that this typed lowering boundary is not itself a durable plan: runtime `Flow` values retain executable procedures, `so` runs inline, and the checkpoint stores data. Resume rebuilds dynamic expansions by replaying callbacks. The current implementation therefore demonstrates deferred model dispatch, but not a fully reified static plan, purity of inline callbacks, or replay equivalence ([runtime flow](../api/vecherinka_runtime.nim), [checkpoint representation](../api/vecherinka_checkpoint.nim), [DSL replay contract](vecherinka_dsl_guide.md)).

The source pass reports that SQLite resume reloads committed artifacts by ID and restores keyed scheduler/checkpoint state; this is durable continuation, not content-addressed memoization. A detailed compatibility pass found that generated workflow identity contains format, workflow ID, normalized `body.repr`, ordered positional flow keys, and artifact type keys; runtime metadata adds prompt-template values and pool names/weights before hashing the JSON with FNV-1a. The body normalizer is an unqualified textual rewrite: every underscore followed by six or more digits becomes `_generated`, including inside string literals. Distinct literals such as `"x_123456"` and `"x_654321"` can therefore normalize identically. Flow keys are positional, assigned recursively, so edits and reordering can renumber them. The manifest does not explicitly include transitive callback/helper code or build/runtime environment; these omissions are inferred from the serialized manifest fields. Resume identity therefore needs careful redesign before being treated as a proof of code compatibility. See [`vecherinka_comptime.nim`](../api/vecherinka_comptime.nim) and [`vecherinka_runtime.nim`](../api/vecherinka_runtime.nim).

Dynamic `so` expansions are rebuilt by replaying callbacks with saved input and budget snapshots. Current reconstruction checks the sorted flow-key set and, only when a stored expansion row exists, a graph signature. That signature omits `fk_raw.value`; older schema migrations may leave no signature row, allowing key checks without signature checks. The DSL documents callbacks as deterministic and side-effect free, but the current Nim type system does not prove purity. These structural checks are not proof of replay equivalence. A correct proof of lossless recomputation would need to account for the full saved input and relevant environment, workflow/code version, codec semantics, raw values and identities, scheduler/budget/checkpoint transitions, failures, and observable history—not just equality of returned values.

A recovery kernel modeled the checkpoint/artifact/attempt/join state and six crash cuts. Local artifact, attempt, work/join, and checkpoint rows commit atomically in a SQLite transaction, but remote model/process effects remain outside it: persisted Submitted means “may have been sent,” so resume cannot distinguish non-acceptance from accepted-but-unacknowledged work. Outbox/event history improves local replay but cannot create remote exactly-once semantics without receiver idempotency or authoritative reconciliation. The store’s owner lease is exactly 30 seconds from the last persisted heartbeat; once stale, `start_execution` can take over before loading the checkpoint. Since `so` runs inline and heartbeat refresh follows event handling, a blocked callback may stall heartbeats while the prior process is still alive, allowing a second resume to take ownership; this is a source-ordering inference, not a reproduced incident. The report also distinguishes application-process crash from OS/power-loss durability because WAL is configured without explicit `synchronous` mode. Its crash table and safety/liveness assumptions are in [crash recovery correctness](/Users/alex/areas/temp/fstar-pulse-research/crash_recovery_correctness.md); no crash injection was performed.

The compatibility pass also found that runtime metadata gates codec and checkpoint payload versions, while resume reads a checkpoint row's `format_version` without comparing it to an accepted version; the writer rejects non-current row versions. This leaves row-version validation policy unresolved. A previously submitted model attempt is restored as unknown and resubmitted using its saved request ID; provider-side idempotency or outcome resolution is not established by the local files. Model calls remain external effects, so local SQLite state alone cannot establish exactly-once execution. See [`vecherinka_store.nim`](../api/vecherinka_store.nim), [`vecherinka_checkpoint_adapter_impl.nim`](../api/vecherinka_checkpoint_adapter_impl.nim), and the [SQLite storage pivot](sqlite_artifact_storage_pivot.md).

A focused pass on durable dynamic expansion confirms that current `so_budget` receives a budget snapshot, checkpoints serialize it, and resume invokes the callback with that saved snapshot. It proposes treating the resolved expansion as a durable decision: record stable expansion identity, saved input/snapshot, builder version, canonical plan, and complete graph hash before children run; replay from that record, optionally rerunning a pinned pure builder only as a consistency check. The report also cautions that its own typed-`Expand` and effect-handler snippets do not yet encode this contract, so the proposal is not demonstrated end to end. This is a useful invariant to compare with an expansion-snapshot representation, not a selected design ([formalism/dynamic-expansion report](/Users/alex/areas/temp/fstar-pulse-research/workflow_formalism_comparison.md)).

The kernel explored one concrete type-level API generalization: define `Shape = Id | Seq Shape | Option Shape` and `Carrier<Shape,A>`, then type `Traverse<Shape,A,B>` so a pure mapper changes both endpoint types while preserving the container/nesting shape. For example, nested `Seq<Option<A>>` maps to `Seq<Option<B>>`; a simple shape-preserving `Map : A -> B -> X -> X` cannot express that. This matches the current `lift` pattern's independent endpoint transformation but remains pseudocode backed by F* indexed-datatype documentation, not a compiled Pulse encoding. Its proposed `CodeRef` names registered code and explicit encoded captures rather than serializing closures. The report does not resolve async traversal, captured-environment compatibility, changed-binary resume, or the requested broader set of examples; see [higher-order plan boundary](/Users/alex/areas/temp/fstar-pulse-research/higher_order_plan_boundary.md).

For a static F*/Pulse authoring model, the source-grounded comparison treats these as alternatives, not a decision: (1) a first-order tagged plan with serializable payloads and an exhaustive interpreter is a clear persistence boundary but needs explicit dispatch and typed packaging/codecs; (2) typed higher-order combinators improve authoring, while arbitrary closures/captures need explicit defunctionalization or replay rules because a closure is not a stable persisted identity; (3) indexed/free-plan encodings can express typed composition and effect boundaries, while serialized checkpoints still need stable witnesses, codecs, and evolution rules. F* documents first-class functions and indexed inductive types, so ordinary typed constructors and an interpreter appear expressible without Meta-F*; higher-order builders can potentially lower into durable node tags while helper functions remain transient ([F* functions](https://fstar-lang.org/tutorial/book/part1/part1_getting_off_the_ground.html), [indexed types](https://fstar-lang.org/tutorial/book/part2/part2.html), [HOAS](https://fstar-lang.org/tutorial/book/part2/part2_phoas.html)). This is a feasibility inference, not a demonstrated end-to-end extraction or resume result. The source-based analysis did not establish that arbitrary effectful code can be safely replayed.

The official guide demonstrates stateful extraction, but no client OCaml version matrix or canonical supported link recipe was found. The scratch shim is not evidence of preserved ownership semantics. A targeted kernel feature probe used installed F* 2026.08.09 and OCaml 5.3.0. Six samples—higher-order argument/return/captured closure, Pulse higher-order function, pure recursion, mutable capture, `pts_to` stateful effect, and ghost/refinement erasure—all typechecked and extracted with verification conditions discharged. A saga/compensation pass treats effect properties as composable capabilities (`Pure`, `Idempotent`, `Reconcilable`, `Compensable`, `Irreversible`) rather than exclusive labels. Persist forward intent before dispatch and outcomes before dependents; resolve every launched forward action before deciding rollback; never compensate an `Unknown` effect speculatively. Run valid compensations in reverse dependency order with stable IDs and their own durable attempts/Unknown state. Model turns, charges, and generated-program external effects are irreversible by default; cleanup can remove only proven-owned resources after termination is established. Sagas help only where an inverse restores a stated invariant and can fail safely; they do not erase model history or create exactly-once semantics. A proposed pilot is a provider-neutral two-call → pinned build/run → artifact commit workflow with crash injection around dispatch, output collection, commit, and inverse dispatch. The current API has model `Prepared/Submitted/Unknown` states but no process or compensation nodes. The report leaves open whether `Unknown` is public API state or runtime-internal and what reconciliation contract adapters must declare ([saga/compensation report](/Users/alex/areas/temp/fstar-pulse-research/saga_compensation_for_workflows.md)).

A session-types/typestate comparison models the Codex client as indexed states for Cold/Initialize, Ready, Thread Idle, Turn Pending/Running, Tool Pending, Interrupt Pending, Unknown, and Closed. With sealed constructors and a checked wire decoder, either F*/Pulse or a conventional private-constructor state machine can locally enforce call order, one active turn per thread, identifier correlation, and one-use tool-reply capabilities. The report finds that signatures alone are not proofs, and session types cannot prove remote receipt, event completeness/order, remote exactly-once effects, or the result of a lost reply. The current client has no request constructors for thread resume, turn steer, or turn interrupt; restored workflow checkpoints do not restore a live Codex process or pending-RPC map. Thus define whether “resumable” promises logical workflow restoration only or continuity of the provider-side thread/turn. It also flags inline tool callbacks as a scheduler blocking boundary and asks which reducer/scheduler invariants need proofs specifically to justify F*/Pulse over a checked ordinary state machine. A focused backend-boundary pass recommends three layers: a typed public `ModelOp<I,O,C>` operation, adapter capability preflight, and an internal event/state machine such as `step(State, Event) -> (State, Seq<Command>)`. A one-shot future is too weak to persist Pending, cancellation, tool handshake, or Unknown. Keep orchestration `OperationId`, dispatch `AttemptId`, JSON-RPC, thread, turn, and tool-call IDs distinct; expose Unknown by default and permit at-least-once duplicate risk only as recorded policy. For JEV-like interaction, a typed state artifact to typed decision is plausible, but multi-turn history ownership and in-flight reconciliation are unestablished. The kernel found a concrete omission in its own proposed `ModelOp`: it must carry the prompt/instruction payload and template identity to encode the existing API. It also found the local client lacks `thread/resume`/`turn/interrupt`, and teardown sends `thread/stop` then kills the server without waiting for terminal evidence; restoring transcript history would not reconcile a lost operation. These findings and blockers are in the [backend-neutral interface report](/Users/alex/areas/temp/fstar-pulse-research/backend_neutral_llm_interface.md).

For backend independence, the source pass traces a Codex-bound path from profile and generated model submit closures, through dynamic `finish_work` schemas and owner-thread output validation, to typed artifacts; artifact lineage, checkpoints, attempts, worker sessions, and correlated conversation events have separate representations. It frames two design placements without selecting one: generic workflow operations with backend adapters preserve direct author code and put protocol/lifecycle/reconciliation details behind adapters; a protocol-neutral operation IR makes pending states, effects, identity, and checkpoint requirements explicit for lowering but may add a second language and complicate captured-closure reconstruction. Neither is yet shown to satisfy all goals. The meaning of JEV-like interaction is also unresolved; it could require a typed state-to-decision call or a stateful exchange, and its history could be reusable typed artifact data, protocol/session records, or both.

For the Codex boundary, source-grounded protocol research found that Codex app-server v0.160.1 accepts optional `clientUserMessageId` on `turn/start` and `turn/steer`, passes it to the core, and echoes it on a user-message item. This supports input-item correlation, but the reviewed contract does not define it as an operation deduplication key or an outcome lookup key. A version-pinned test shows that `thread/read` and default `thread/resume` return a client ID already present in stored history; this proves history projection, not that every accepted turn is persisted before a crash, nor uniqueness or retention across compaction/rollback. The local wrapper sends no client ID and does not implement thread read/resume. A supplied ID can conditionally correlate a stored item if the client loads the relevant turns/items, but a no-match is inconclusive and cannot authorize retry as definitely unaccepted. The official guide also documents turn interruption, but the wrapper has no turn-interrupt operation or per-request timeout. It correlates replies only with in-memory JSON-RPC IDs; the protocol specifies request/response correlation, not durable operation identity. During initialization, the server returns `userAgent` and platform data; `clientInfo.version` and capabilities are client-declared, with no separate negotiated server protocol version. A future attempt record should evaluate persisting the resolved executable path/version, observed server `userAgent`, and client protocol/schema revision.
