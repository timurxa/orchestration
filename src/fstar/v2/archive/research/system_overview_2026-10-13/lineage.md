# Lineage: original F* workflow API proposal to v2 contract

**Purpose.** Evidence for a later user-facing guide. This report compares the two v2 planning artifacts with the proposal and only linked predecessor documents needed to identify that proposal. It does not draft the guide or claim implementation proof.

## Executive finding

There is no single predecessor called “the original spec.” The documents form a chain with different authority:

1. [`src/docs/fstar_pulse_workflow_api_problem_spec.md`](../../../../../docs/fstar_pulse_workflow_api_problem_spec.md), especially **Assignment and scope**, **Required workflow behavior**, **Durable state and continuation**, and **Expected result**, defines target requirements. It explicitly says it is a problem input, not an API design. It also says older Pulse/provider research is historical and out of scope where inconsistent.
2. [`src/docs/fstar_typed_plan_workflow_api_outline.md`](../../../../../docs/fstar_typed_plan_workflow_api_outline.md), **Selected kernel**, gives the compact original typed-plan API proposal (`pure`, `then_flow`, `fork`, `lift`, `external`, `so`) and reports a prototype status. It is a design summary, not the authoritative requirement set.
3. [`src/docs/fstar_typed_plan_workflow_api_report.md`](../../../../../docs/fstar_typed_plan_workflow_api_report.md), **Selected API** and **Alternative formulations reviewed**, expands that proposal and corrects an outline error: `Lift` cannot express two distinct same-input branches, so `Fork` is needed. It also documents that prototype as incomplete against the problem specification.
4. [`src/docs/fstar_workflow_api_next_research_spec_draft.md`](../../../../../docs/fstar_workflow_api_next_research_spec_draft.md), **Objectives**, **Dataflow API research**, **External operations**, **Resources**, and **Durable execution and proof obligations**, is a successor research/design brief. It is not merely another name for the outline. It adds explicit dependent-contract, adapter/resource, and recovery decisions for later research.
5. [`src/fstar/v2/implementation_spec.md`](../../schema_era_2026-10-14/implementation_spec.md) is the v2 normative abstract contract; its opening status says v2 source files are partial evidence, no source theorem is currently discharged. [`implementation_packet.md`](../../schema_era_2026-10-14/implementation_packet.md) is subordinate and assigns module boundaries, proof order, decision rules, and acceptance checks; it explicitly claims no theorem proved.

**Interpretation used here:** “original proposal” means the typed-plan kernel summarized in the outline, read alongside the problem specification that governed it and the report that corrects it. Comparing v2 only to the outline would miss both its original requirements and the proposal’s documented correction. Comparing v2 to the research draft surfaces additional successor decisions and departures.

## Retained decisions

- Exact-input typed output families remain core; local code is total and pure; external effects cross explicit adapter boundary. Sources: problem spec **Required workflow behavior**; research draft §§3, 6; v2 §§2, 2.1.
- Runtime construction/generation is pure; effects do not occur while building graph. Sources: problem spec **Required workflow behavior**; draft §6; v2 §2.2 and §2.1.
- Durable recovery must preserve committed work, route/graph choices, typed outputs, budget, and artifact identity. Sources: problem spec **Durable state and continuation**; outline **Durable model** (with admitted gaps); v2 §§4–5, P10/P16.
- Independent ready nodes/calls may progress and complete out of order, with ordered typed composition/output semantics. Sources: problem spec **Required workflow behavior**; draft §§6, 8; v2 §§2.2, 4.2–4.3, P15.
- Never serialize native closures or live process handles as durable workflow data. Sources: problem spec **Durable state and continuation**; draft §§6–7; v2 §§2.2–3.
- Local IDs alone do not prove remote exactly-once effects. Draft §6.1 and v2 §2.1/P7 both require a keyed effect-safety argument, though v2 narrows its admitted outcome model.

## Changed decisions

1. **Closure-backed typed plan to graph-description core.** Outline/report proposes closure evaluator and `so` route returning a value or child reference. V2 has `LocalWork`, `ExternalWork`, `GenerateWork` and first-order `GraphDesc`; code needed for transformations is represented as registered work nodes. Durable recovery resolves graph syntax rather than restoring a workflow closure. See report **Selected API**; v2 §§2, 2.2 and §8.
2. **Unknown outcome removed from durable model.** Draft and prototype report model pending/unknown/reconciliation and `NotApplied`; v2 permits only effect-safe same-key resume to one outcome, excludes irreconcilable effects, has no `Failure` event, and stores expected domain failure in result type. See draft §6.1; v2 §§2, 2.1, 4.1.
3. **Proof standard elevated from prototype observations to explicit theorem split.** Outline’s prototype had replay consistency but unauthenticated header and process-local event queue. V2 distinguishes abstract journaler/P10 from host/extraction P13, and semantic provenance/P16 from replay-only state. See outline final paragraph; report **State, adapters, and persistence** and proof ledger; v2 §§4.4, 6, and packet §§5–6.
4. **Kernel artifact model is abstract.** Prototype placed Blob checks in core and had codec-validation gaps; v2 excludes Blob and handles as primitive and uses typed artifact packages with optional P9. See report **Artifact decisions**; v2 §3 and P9.

## New decisions in v2

- A pinned registry manifest is exact canonical projection of executable packages; identities must uniquely resolve complete linked code/schema/codec/adapter/resource/root contracts (spec §2, P0).
- Graph edge typing must hold universally for every legal port environment, not only sampled execution values. Schema support is explicit and finite; graph resolver reconstructs proofs (spec §§2.2, 6 P1–P2; packet §6).
- One journal is sole durable authority; event payload omits duplicated state and derives projections by replay. Separate append authorization preserves semantic origin (spec §§4.1–4.3).
- Concurrent execution is modeled across all permitted interleavings with unique claims, current-head reauthorization, crash epochs and serial journal commits (spec §§4.2, 6 P15; packet §5).
- All-cut recovery is split into canonical byte/prefix theorem P10, runtime refinement P13, semantic recovered-graph theorem P16, conditional termination P14 (spec §§4.4, 6).
- Dynamic generation carries explicit per-occurrence charge/fuel plans; P8 proves conservation and P12 proves a decreasing rank (spec §§2.2, 4.3, 5, 6; packet §5).

## Deferred or still open

- Concrete F* encodings for heterogeneous dependent ports, existential packages, schema normalization/equality, graph builder representation and canonical node keys (spec §8; packet §7).
- Concrete journal, worker/controller, adapter, extraction and artifact-store refinements; P13/P10/P7/P9/P14 laws depend on those implementations (spec §6 contract boundary; packet §§5, 7, 10).
- Which resource types need P9 and their concrete publication/reacquisition/materialization semantics (spec §3, P9; spec §8).
- Library combinators (`then`, `fan`, `lift`, `case`) and inline-vs-library adapter packaging (spec §§8–9; packet §7).
- Whether v2’s finite graph syntax fulfills the original requirement that `so` child computations use ordinary F* “everywhere.” V2 requires ordinary total F* generator/work callbacks but persists and interprets graph-description syntax. The docs do not explicitly reconcile this wording or explain whether it is an intentional weakening, an equivalent encoding, or a revised API boundary.
- The draft’s durable unknown/reconciliation policy is absent. V2 does not state an equivalent terminal `Unknown` checkpoint; it instead excludes irreconcilable adapters. This may be acceptable API narrowing, but no migration rationale is supplied in the examined artifacts.

## Strongest objection

**Potential scope mismatch:** original problem spec expressly requires ordinary F* inside dynamic `so`; the outline/report’s selected API meets this through ordinary total callbacks and a compiled child resolver. V2 makes generated children first-order `GraphDesc` values resolved by a finite manifest-pinned schema language. While callbacks/generator remain F*, the durable child workflow is constrained to graph syntax. Unless guide explains why this still meets the “ordinary F* everywhere” requirement, presenting v2 as a straightforward implementation of the original proposal overstates continuity. The unresolved `Unknown` removal reinforces that v2 is a revised contract, not simple maturation.

## Unresolved issue for guide author

State whether “original proposal” means (a) typed-plan outline, (b) governing problem specification, or (c) next research draft. Best factual framing: explain all three layers and authority. Need design owner answer on whether graph syntax is intended equivalent realization of `so` or deliberate replacement, and why draft’s durable `Unknown` state was removed. Until answered, guide should label those as changes/unresolved, not silently claim retained behavior.

## Assumptions and evidence limits

- Section references identify documentary evidence; no unlinked implementation or research artifacts were inspected.
- “Retained/changed/new/deferred” are comparative classifications inferred from the named documents, not explicit labels in the source.
- V2 spec/packet describe normative targets and planned proofs. Their signatures, contract fields, packet checklists and existing partial source do not establish those theorems. The documents themselves say no P0–P16 theorem is yet discharged and concrete refinement remains separate.
- The original outline is a summary with a known `Fork` correction in its linked report; report is used only to resolve that defect and prototype status.
