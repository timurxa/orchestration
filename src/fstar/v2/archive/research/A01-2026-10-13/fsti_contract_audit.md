## Evidence

- **Installed tool:** no `fstar.exe`, `FStar.exe`, or `fstar` is on `PATH`; no `.fsti` exists under `src/fstar/v2/src`. I therefore checked interface behavior against official F* documentation, not a local compiler experiment.
- **Official F* behavior:** an `.fsti` is paired with a same-module `.fst`; it may expose abstract types and `val` declarations, and paired implementation supplies definitions checked against those types. An interface may contain definitions too. A module with an interface has at most one implementation; an interface without implementation is an assumption/axiom. The official tutorial also documents an ordering constraint: implementation definitions must follow the order of interface `val`s because F* interleaves the two halves. [F* Interfaces](https://fstar-lang.org/tutorial/book/part3/part3_interfaces.html#interfaces), [F* Modularity](https://fstar-lang.org/tutorial/book/part3/part3.html).
- **Official trust behavior:** `assume` tells F* to accept a proposition without proving it; `admit()` can inhabit any expected type. The tutorial says proof work is unfinished until both are removed. [F* Assertions and Assumptions](https://fstar-lang.org/tutorial/book/part1/part1_prop_assertions.html#assumptions).
- **Current source trust findings:** `Graph.fst` has `assume type graph_builder` and `assume val` declarations for `builder_nodes`, `start_graph`, and `add_node` (`Graph.fst:417-424, 523-530`). Four builder/P1 lemmas end in `admit()` (`Graph.fst:908-956`). These are active trusted holes in ordinary `.fst` source, not merely abstract interface declarations. Current source has no `.fsti` pair to audit.

Full project command is `make -C src/fstar/v2 verify`; unavailable here because executable is absent from `PATH`. ## Safe interface policy

1. Use `.fsti` only where a downstream proof needs a stable, intentionally abstract API. Keep kernel syntax, public predicates, contract-record types, and signatures there; keep private induction helpers and proof terms in paired `.fst` or internal proof modules. Modules without `.fsti` reveal all declarations, so use that for internal nodes where abstraction buys little.
2. Every `.fsti` must have exactly one same-name `.fst`, both checked in the full build. Treat an unpaired interface as an axiom and disallow it for all P0–P16 dependency closures. A `.fsti` `val` is not itself evidence of implementation or theorem completion; record its paired body and the build that checked it. Preserve interface `val` order in implementation definitions per F*’s interleaving rule.
3. Put each P theorem’s exact proposition in the contract surface; pair it with a checked proof body. External services are explicit theorem parameters: define records whose operation fields and law fields are supplied as values/proofs. A generic theorem may conclude “given `J` satisfying law …,” but a concrete instance must construct `J` and its proof fields. Never make the service law a free `assume val` hidden in a `.fsti`.
4. Expose interfaces at acyclic proof seams only. Preserve the packet’s order: `ManifestCore` before `Schema`/`GraphResolve`; resolver does not import `Bundle`; `GeneratorAdmission` does not import `GraphBuilder`; `Journal` does not import controller/provenance proofs; keep P4/P8/P15/P16 consumers one-way (`implementation_packet.md:242-290`). Prefer `.fsti` for these stable API seams, not for every helper module.
